# Бэкапы Postgres в S3

Небольшой стенд для Laravel-приложения: Postgres 16 и S3-совместимое хранилище (SeaweedFS) в docker compose, плюс два скрипта: backup.sh делает дамп и кладёт его в S3, restore.sh проверяет, что из последнего дампа можно реально поднять базу.

Запуск:

    cp .env.example .env        # поменять пароли
    docker compose up -d --wait
    ./backup.sh
    ./restore.sh

На хосте нужны docker compose и aws cli. Тестовые данные (5000 клиентов, 20000 заказов, 50000 позиций) создаются при первом старте из db/init. В cron backup.sh ставится обычной строкой, например `0 * * * * cd /opt/backup && ./backup.sh >> /var/log/backup.log 2>&1`.

Как это работает. backup.sh делает pg_dump в custom-формате, проверяет его через pg_restore --list, грузит в S3 и сверяет размер загруженного объекта. Рядом кладётся манифест с sha256 и количеством строк в ключевых таблицах. Манифест пишется последним, поэтому оборванная загрузка не считается бэкапом и restore.sh её не выберет. Старые объекты (по умолчанию старше 30 дней) удаляются только после успешной загрузки, и текущий бэкап не трогается. restore.sh берёт последний манифест, проверяет sha256, восстанавливает дамп во временную базу с --exit-on-error, смотрит, что все таблицы на месте, не пустые и содержат не меньше 95% строк от того, что было перед дампом, и что внешние ключи валидны. При любой проблеме он выходит с кодом 1, временную базу удаляет в любом случае, боевая база не затрагивается.

SeaweedFS вместо MinIO, потому что образы MinIO в Docker Hub сейчас не скачать. В проде S3 должен быть внешним, иначе вместе с сервером умрут и бэкапы; в compose он нужен только для проверки скриптов.

## Сервер умер. Как и за сколько поднимаешь, сколько данных теряем?

Поднимаю новый сервер, ставлю Docker, клонирую репозиторий, беру .env из менеджера секретов (не с умершего сервера) и запускаю docker compose up -d --wait. Потом гоню restore.sh, чтобы убедиться, что последний бэкап рабочий, и заливаю его pg_restore в боевую базу. Потеряем всё, что было после последнего бэкапа: при почасовом cron это до часа, а чтобы уложиться в минуты, нужна архивация WAL (pgBackRest или WAL-G), здесь её нет. По времени подготовка сервера занимает 15–30 минут плюс загрузка дампа, которая зависит от размера базы; restore.sh печатает свою длительность (на тестовых данных около 8 секунд), так что реальную цифру для боевой базы надо снять замером. Redis и очередь поднимаются из compose, их состояние не критично.

## Диск заполнен на 95%. Что делаешь по шагам?

Сначала смотрю, что занимает место: df -h, du -xh --max-depth=1 /var/lib/docker | sort -h и docker system df. Потом освобождаю только то, что можно безболезненно получить обратно: docker image prune, docker builder prune, архивирую логи приложения и nginx, чищу журнал (journalctl --vacuum-size=200M). Тома и docker system prune --volumes не трогаю. Если растёт WAL, ищу отставший слот репликации или сломанную архивацию в pg_replication_slots, а файлы из pg_wal руками не удаляю. После этого увеличиваю диск и ставлю алерт на 80%.

## Как защитить бэкапы, если кто-то получит доступ к серверу?

Серверу нельзя давать право стирать или читать историю бэкапов: отдельный S3-пользователь только с PutObject и ListBucket, бакет в другом аккаунте, включённые versioning и Object Lock, а старые дампы удаляет lifecycle-правило самого бакета. Дамп шифрую до загрузки публичным ключом (age или GPG), приватный ключ хранится вне сервера, тогда даже доступ к бакету ничего не раскрывает. Ключи S3 лежат только в .env с правами 600 и периодически меняются. Ещё нужен алерт, если свежего бэкапа нет, и регулярный запуск restore.sh: непроверенный бэкап бэкапом не считается.

В этом стенде для простоты одна admin-учётка S3, а шифрования и Object Lock нет, то есть последний абзац описывает целевую схему, а не то, что уже реализовано.
